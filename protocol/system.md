# The system

How every service's [records](records.md) are read as one system, and the index
that comes out — `specrig: index/1`. One tool does it for every stack:
`specrig-flows`, released with [specrig-go](https://github.com/specrig/specrig-go)
for each platform.

```
specrig-flows <root> <index.yaml>
```

## The set

Every directory below `root` holding `tests/surface.yaml` or `tests/flows.yaml` is
a service, whatever its stack; what lies inside it is not searched further. Hidden
directories, `vendor`, `node_modules` and `testdata` are passed over. A file at a
record's path that does not open with `specrig:` is somebody else's, named and
passed over; a record that does and cannot be read, or is newer than the tool
reads, fails the run, and so do two surfaces of one service.

The set is the whole system. A service with `flows.yaml` is **traced**; one with only
`surface.yaml` is in the check of the code and sends nothing a flow can follow. A
party with no record is outside.

## How a message is received

A message a traced service sends is received by every input of the same message in
another — an event by its sender's own too, since a service takes its own events
through the bus like anyone's. A writer names an HTTP request it sent by the route
of the contract that takes it, so the names meet.

In the code, from the surfaces:

| kind | what takes it |
|---|---|
| event | a binding of the same key, or one with `*` or `#` that takes it by the AMQP topic rule — a **wildcard** |
| gRPC | a service serving the method |
| HTTP | a route of the same method, or `*`, segment by segment: `{…}` in the route or `{}` in the request takes any segment, `*` at the route's end takes the rest, the query is ignored |

An HTTP request whose path does not start with `/` — onto a base URL configuration
sets, `external` — lands nowhere, and a route with nothing constant in it — `/*`,
`/{x}`, under a prefix configuration sets — is no evidence that a request lands on
its service. A **client's host** is the service whose routes take most of the
client's requests or, for a party outside the set and on a tie, the one
`flows.clients` in the caller's `specrig.yaml` names; the client's requests land
there only.

## Flows

A flow starts at a **way in**: every `http` and `command` input, and any other input
no other traced service sends — for an event, none at all. It holds every step
reachable from there through the branches, depth first, a step right after the
first message that reaches it. A flow is written only if its way in sends something
a traced service receives.

A step further on takes its branches as what reaches it allows. What reaches it are
the fields under `sent` of the branches its senders take, grown until they stop
growing; a message whose `needs` are not all among them is not followed, and a
branch that sent it stays only when it was refused or sends something no unaffected
branch does. The way in is taken whole.

A flow's **id** is `<service>-<kind>-<name>`: lowercased, Cyrillic transliterated
(а a, б b, в v, г g, д d, е e, ё e, ж zh, з z, и i, й y, к k, л l, м m, н n, о o,
п p, р r, с s, т t, у u, ф f, х kh, ц ts, ч ch, ш sh, щ shch, ъ —, ы y, ь —, э e,
ю yu, я ya), every run of anything but `a`–`z` and `0`–`9` one `-`, trimmed. A gRPC
method is named `Service.Method`; where two steps would share an id, by the whole
name; where they still do, the id takes `-` and the first six hex digits of the
SHA-256 of the step, `<service>: <message>`. A page is named by the same rule.

## The index — `specrig: index/1`

```yaml
# Generated by specrig-flows. Only the title and description of a flow are yours.
specrig: index/1
flows:
  - id: shop-http-post-orders
    title: Placing an order
    description: The stock is held before the order is taken.
    entry: 'shop: http POST /orders'
    from:
      - portal
    steps:
      - 'shop: http POST /orders'
      - 'stock: grpc /stock.Stock/Reserve'
links:
  - from: shop
    to: stock
    message: grpc /stock.Stock/Reserve
    notes:
      - 'the receiver''s cases send fields the sender never does: items[].count'
untested:
  - 'shop → stock: grpc /stock.Stock/Release'
outside:
  - 'billing sends http POST /payments: out of the system'
system:
  outside:
    - POST /payments (by billing, to acquirer)
```

| key | what |
|---|---|
| `flows` | by way in: the `id`; `title` and `description`, written by hand and kept by `id`; the way in, `<service>: <message>`; `from`, the services whose code sends it; the steps |
| `links` | by sender and message: what one traced service sends and another receives; `notes` names the fields the receiver's cases send and the sender's never do, a scalar where the other side has an object aside |
| `untested` | a link the code has between two traced services and no case follows: an event bound exactly, a gRPC method — outgoing HTTP is not traced |
| `outside` | what a traced service sends that no traced service received: `received by …, no case took it`, `only a wildcard subscription: …`, `out of the system`, or `not traced` when no service has a surface |
| `system` | the surfaces against each other, when any service has one; `{}` when that finds nothing |
| `orphaned` | a flow's prose whose flow is gone, under the anchor `flow <id>`; it comes back with the flow |

`system`:

| key | what | the run |
|---|---|---|
| `unconsumed` | an event published, bound by nobody | fails |
| `unpublished` | an event bound, without a wildcard, published by nobody | fails |
| `unserved` | a gRPC method called and served by nobody; an HTTP request its client's host does not route | fails |
| `uncalled` | a gRPC method served and called by nobody — a route nobody requests is a way in | fails |
| `ambiguous` | an HTTP request more than one service routes | fails |
| `hostless` | a client none of whose requests the set routes, not in `flows.clients` | fails |
| `needless` | a `flows.clients` key with no such client, or naming the host the set tells | fails |
| `pattern_only` | an event taken by a wildcard alone | tells |
| `loops` | a service binding an event it publishes | tells |
| `outside` | an HTTP request no service routes, `to <host>` when its client names one outside the set | tells |

`flows` is written even when it is empty; any other key with nothing under it is
left out, and the order of a list is the one the fixtures show.

## The run

The index is written at the path given and a page beside it for every flow and for
every step a flow reaches; a file already holding what would be written is left
alone. A page whose first line says the tool wrote it and that it would not write
now is removed, and each link lost or new since the index already there is named.
That index is read for its prose only if it says `specrig: index/1`; anything else
at the path fails the run.

The run fails, after writing, while `orphaned` holds anything or `system` holds what
fails.

**Pages** are for people. A flow's page draws the sequence, the branches under the
arrow that reached them and the condition that made them, and the cases of its own
input with the comment above each in its `.feature` file — the file the case names,
found anywhere below the service's `tests/`. A step further on lists its branches
and links to its own page. A message not followed is a note on its step: either it
cannot be sent there, or its receiver has no case sending it with what the flow
carries — a gap to close either way. The text of a page is the tool's.

## The fixtures

`fixtures/flows/<name>/` is one run: `set/` the services, `before.yaml` the index
already at the path if there is one, `index.yaml` what the run writes — its header
word for word, then the same document — and `expect.yaml`, `specrig:
flows-fixtures/1`, with the names of the pages written and whether the run fails.
The tool runs them.
